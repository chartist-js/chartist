# Decisions

The standing decisions behind Chartist: what holds today and why. Detailed behavior is in the living specs (`openspec/specs/`). When the author decides something new, add it here with its reason, or change the entry it replaces.

## History

Chartist.js started in 2014 (0.x): plain JavaScript, Sass, "style with CSS, control with JS", and a hand-crafted docs site with the Chartist Guy and live examples (archived under `/v0/` of chartist.dev; reference clone `tmp/chartist-v0`). In 2022, Cube sponsored the move to TypeScript, Rollup and pnpm (1.x) with a Docusaurus site at chartist.dev (reference clone `tmp/chartist-v1`). v2 rebuilt the library on a functional, composable core, brought back the 0.x site's personality with a new brand, and kept 1.x code working. The rebuild happened in the same repository, so the history back to 2014 is intact; the archived OpenSpec changes in `openspec/changes/archive/` are the detailed record of how and why.

## Principles

- **CSS-first.** Style with CSS, control with JS. Charts are plain SVG with predictable classes; colors, lines, grid and labels are `--ct-*` custom properties. Options don't duplicate what CSS can do, and output has no inline `style` attributes. Default colors follow the page's `color-scheme` through `light-dark()`, not the OS setting (decided 2026-10-16): a light page stays light in dark mode, and a page that declares dark gets light labels and grid lines.
- **TypeScript-native.** The library is written in TypeScript and its types are part of the API. Docs examples are small HTML + TypeScript + CSS projects in the shape of an `npm create vite` vanilla TypeScript app (`index.html`, `src/main.ts`, `src/style.css`), so they open in StackBlitz or a fresh Vite app unchanged. They use only erasable TypeScript syntax and `import type`, so the browser playground can strip types with sucrase.
- **No bundler required.** `<script type="module">` with ESM from a CDN is the primary no-bundler path, shown in Getting started next to npm. UMD ships for backwards compatibility only (documented in "Coming from 1.x", never in examples); CJS for older Node tooling.
- **Functional API first.** `chart()`, `lineChart()`, `barChart()`, `pieChart()` and layers; the core is pure from config to scene (`toScene()`, `renderToString()`), side effects stay at the edges. Event payloads are read-only: handlers transform by returning a new value. Docs, examples and doc comments use the functional API; the 1.x classes appear only where the text is about 1.x.
- **Small.** Stay the smallest charting library: everything tree-shakes, per-entry size budgets are checked (`test:size`). A budget is raised only on purpose, with the reason in the commit. The bugs found in 2.0.0-rc.1 were fixed even though it costs about 1 kB gzipped across the entries (decided 2026-10-15): fixed behavior beats the bytes.

## 1.x compatibility

- **No breaking changes for 1.x code.** `LineChart`, `BarChart` and `PieChart` are thin wrappers over the presets and draw what 1.5.0 drew; the visual tests prove it against a 1.5.0 baseline.
- **No 1.x export is removed in 2.x.** `Svg`, `SvgList`, `SvgPath`, the helpers and the other 1.x root exports stay available from `chartist` and the UMD global.
- **The 1.x API is deprecated, with removal from `chartist` in 3.0** (decided 2026-10-14). The classes and what exists only for them (axis classes, `EventEmitter`, the 1.x drawing helpers, the 1.x options and event types) carry `@deprecated` with the functional replacement, so editors stop offering `LineChart` next to `lineChart`. Names the functional API uses or documents (data types, `Svg`, `Interpolation`, the helpers) stay. The deprecation is type-level only: no runtime warnings, the UMD global unchanged. The 1.x event and plugin types are also exported, unmarked, from `chartist/compat`. A checked-in list (`packages/chartist/test/api/exports/deprecated.json`) sorts every 1.5 export. Whether the 1.x API disappears in 3.0 or moves elsewhere is decided for 3.0; a separate entry for it in 2.x was considered and dropped, because a deprecation should point forward.
- **`labelInterpolationFnc` is renamed `labelTransform`** (decided 2026-10-16, #215): the old name never said what the function does. Both names work in 2.x and the new one wins when both are set; the old one is deprecated and removed in 3.0. The preset defaults stay on the old name, because the 1.x classes expose their resolved options to 1.x plugins.
- **1.x events and plugins are opt-in** through `chartist/compat`, so the runtime ships no compat code. Without it, using them logs a one-time warning with migration instructions. `fromLegacyPlugin()` brings a 1.x plugin to the functional API, and importing `chartist/compat` sets up the global `Chartist` that 0.x and 1.x plugin scripts expect.
- **New features are functional-API only** (composed charts, multiple axes, SVG text labels, container queries). The classes exist so 1.x users don't break.
- **What 1.x had exists in both worlds** (decided 2026-10-19): every feature from before v2 (options, markup, classes, events) works through the 1.x classes and through the functional API, and a fix to one of them lands in both. A feature added in 2.x needs no 1.x path: the docs, examples and tests show it with the functional API. It isn't blocked from the 1.x classes either: when it is purely additive, leaves 1.x output unchanged and costs nothing to have in both worlds (an option on the shared `AxisOptions`, a v2 plugin or a preset option the classes pass through), it stays available there, without separate v2-only types or tests that reject it. Only what would cost code, size or tests to bring to the classes stays functional-API only.
- **Plugins:** the functional API takes v2 plugins (`{ name, install }`) only; the classes take 1.x plugin functions with `compat`. The most used 1.x plugins get official v2 successors in `@chartist-js/essentials` and `@chartist-js/tooltips` (see "Maintained packages"); other community plugins work through compat and are listed on `/plugins/`. Official plugins were first limited to the ones the author maintained in 0.x (accessibility, point labels, threshold); that changed on 2026-10-19, because axis titles, legends and tooltips are what users install most.
- **Framework support,** when it comes, is a web component in a separate wrapper package rather than one wrapper per framework.

## Layers

- **Reference lines and bands are core layers** (decided 2026-10-16): `targetLine()` and `band()`, the most common additions to line and bar charts, which 1.x left to plugins. They're ordinary layers, so they tree-shake, render on the server and in the terminal, and are styled with classes and `--ct-target-line-*` / `--ct-band-*` properties only. The size budgets were raised for them on purpose.
- **Trend lines are a core layer too** (decided 2026-10-16, #1209): `trendLine()` fits a least-squares straight line per series, drawn in the series' color. Other fits (polynomial, moving averages) are left to custom layers.
- **One target line per layer.** A first version took one line or `lines: [...]` as a union of two option shapes; TypeScript then reported a missing `value` as a wrong `label` type. Several lines are several layers, with plain options.
- **A band edge is a constant, values of its own, or a series.** Own values (an array, one per label) keep edges that aren't data out of `data`, so presets don't draw them as lines and the series keep their colors. A bare number is a constant; a series by index is `{ series: 2 }`.
- **Layers that change other layers' output use `refine`,** an optional layer method in the `compose` phase (decided 2026-10-16): every layer composes independently first, then each node with a role passes through the refining layers in list order, before the `compose` events. List order stays the draw order. A dependency order between layers was rejected: compose order doesn't decide draw order, and layers depend on each other's finished nodes, not their data. A refiner sees one node at a time and can't drop nodes or change the tree; charts without a refining layer skip the step. The band's `mark` option is built on it.
- **Layers reserve room outside the drawing area with `inset()`** (decided 2026-10-19, #1528): a layer returns the px it needs per side, and the room is added to the padding, outside the axis bands, before the axes take their offsets. So the area shrinks and the presets' 1.x label formulas, which place top and left labels from the padding, keep working. Shrinking only the area was rejected for that reason. Layers on the same side stack outward in the order of `layers`, like axes; each gets its boxes as `insetArea`, computed before the `layout` listeners so a listener can't move them, and the `layout` payload reports the room as `inset`. Charts without such a layer lay out exactly as before. It runs before the axes exist, so room that depends on tick labels (#304) needs a step of its own. The hook costs about 0.5 kB gzipped wherever the pipeline is bundled; accepted on purpose, since it lets axis titles and legends live outside the core.
- **Minor grid lines and axis transforms are core concepts** (decided 2026-10-20, #64): an axis can list `minorTicks`, which the grid draws as `ct-grid-minor` lines without labels, and an axis factory can declare an `AxisTransform` (`forward`, `inverse`), in whose results the axis is linear. They're in the core, not in `@chartist-js/essentials`, because any axis can have them, the core's own scale axes could get subdivisions later, and `trendLine()` needs the transform to fit a straight line on a log axis. The minor grid style is in the core stylesheet for the same reason. Both are stable, without `@experimental`. Minor ticks are off by default, so charts look as before. They cost about 140 B gzipped in every cartesian chart; accepted, since minor grid lines also help large charts.
- **Presets take extra layers** with `layers: { below, above }`: below the series (after the grid) or above them (before the axis labels). Two lists, because a band belongs behind the data and a target line in front; the preset's own layers stay private. Responsive entries merge into it like other options, list by list.
- **A listed plugin whose use case the core covers leaves the plugins page,** and its published page redirects to the docs that cover it (`chartist-plugin-targetline` → "Target lines and bands"). `chartist-plugin-threshold` stays: the core doesn't split lines and bars at a value. A plugin replaced by an official package (`@chartist-js/essentials`, `@chartist-js/tooltips`) leaves the page too, without a redirect (decided 2026-10-19); links that pointed to its page point to the package's guide instead.

## Repository

- This is `chartist-js/chartist`, with its stars, issues and history back to 2014. `main` is the development branch. A `1.x` branch, created from the `v1.5.0` tag, holds 1.x maintenance.
- Git doesn't record renames; it infers them from similarity. File moves, deletions and content edits therefore go in separate commits, and branches are integrated with merge commits or a rebase, never a squash merge, which would collapse a move into its edits.
- Formatting is oxfmt with the 1.x Prettier settings in `.oxfmtrc.json`. Reformat-only commits are `style:` commits listed in `.git-blame-ignore-revs`.
- Tooling: Nx 23 with pnpm workspaces; tsdown (Rolldown + Oxc) for the library, Sass + PostCSS for its CSS; oxlint; Vitest; Playwright for visual, e2e and playground tests; Astro with `@geekvetica/nx-astro` and Tailwind v4 for the docs site.

## Distribution

The `chartist` package ships, under `dist/` and through its `exports` map:

- an ESM build for bundlers (`index.js`, side-effect free) and a minified, self-contained browser ESM build (`index.min.js`) for `<script type="module">` and CDNs;
- a UMD build defining the global `Chartist` (`index.umd.js`, also as `chartist.min.js`); the bare jsDelivr and unpkg URLs serve it, as in 1.x;
- a CommonJS build (`index.cjs`) that loads in Node without a DOM;
- type declarations for both module systems (`.d.ts`, `.d.cts`);
- compiled CSS (`chartist/styles.css`), the opt-in accessible theme (`chartist/themes/accessible.css`) and the Sass sources (`chartist/scss/…`);
- `chartist/compat`, `chartist/live` and `chartist/server` in every format, each importing the core instead of bundling a copy.

Every 1.x import path keeps resolving.

The `@chartist-js` packages ship ESM and CommonJS builds with declarations for both, through their `exports` maps, and depend on `chartist` with a `^{version}` range (`workspace:^` in the repository, which `pnpm publish` rewrites).

## Maintained packages

- **The `@chartist-js` npm scope** (decided 2026-10-15) holds the packages maintained next to `chartist`: renderers, plugins and wrappers, each in `packages/<name>`. `chartist` keeps its name. The first is `@chartist-js/terminal`, a terminal and text-art HTML renderer with the `ct-cli` command.
- **`@chartist-js/essentials` and `@chartist-js/tooltips`** (decided 2026-10-19) hold the additions users ask for most, so the core stays small and they're still maintained in this repository and released with it. The core keeps the axes and layers it shipped in 2.0; new axis types and layers go to `essentials`: the axis title, legend and value label layers, and the log and time axes (#64, #116). They tree-shake like the core's, render on the server and take their looks from `--ct-*` properties in the package's stylesheet. Tooltips are their own package, a plugin rather than a layer: they're pointer and focus interaction in the browser, with nothing to render on a server. The 2.x plugin download numbers decided the list: tooltips (three forks together), axis titles, legend and point labels lead by far. Layers that need room outside the drawing area (axis titles, a legend) reserve it through the public layer API, which the core extends for them, so the packages use nothing internal.
- **`@chartist-js/essentials` is stable from its first release, 2.2.0** (decided 2026-10-19): its exports build on the stable layer contract, so none is `@experimental`; a later addition may mark its own. Its examples get a gallery section of their own, "Essentials", after "Live data", and the examples check keeps the package's examples there.
- **`logAxis()` draws zero and negative values at the axis start** (decided 2026-10-20, #64): they're left out of the range and placed at 0 px, rather than throwing (as `chartist-logaxis` did, which broke bar charts through their reference value 0) or becoming holes (which would need every layer to ask the axis). One zero in live data never breaks a chart, bars grow from the bottom edge, and `null` gives a gap. A `base` of 1 or less and a `low` or `high` of zero or less still throw, since they're mistakes in code. The range doesn't drop one more power when the smallest value is exactly a power, and there's no built-in `10³` label format; `labelTransform` covers it.
- **`@chartist-js/tooltips` is a plugin, shown in the top layer** (decided 2026-10-19, #1530): a tooltip is interaction in the browser, with nothing to draw on a server, so it's a v2 plugin, not a layer. It's a `popover` in the chart's container, so `overflow: hidden` can't clip it and the container's custom properties and `color-scheme` still apply, placed through the CSSOM so it works under a strict policy. Content is text by default; `render` fills it with your own DOM or a framework's template, with a cleanup, and `format` still names the value for screen readers (returning `undefined` keeps the default text, so a `format` can handle some roles only). Any role can have a tooltip, the roles of other layers and packages included: the plugin works from the scene, and `format` and `render` get the node's context typed by the listed roles, so checking `item.role` narrows it. Keyboard access is on by default, as one tab stop per chart with arrow keys between values (WCAG 2.1.1). It imports only types from `chartist`, so its browser build needs no import map. Its browser smoke test checks only what jsdom can't (the top layer, focus, the strict policy); placement and touch are unit-tested (the author asked to keep it lean).
- **Without a bundler, packages load through an import map** that maps `chartist` and the package to their `dist` files on jsDelivr (decided 2026-10-19): the package imports `chartist` by name, so the map gives it the page's copy. jsDelivr's `/+esm` was rejected: it rewrites that import to an exact-version URL, which loads a second copy of the core next to the page's (checked on `@chartist-js/terminal`).
- **Shared code goes through `chartist`'s public API**, not a shared internal package (decided 2026-10-15). What a renderer needs is exported from `chartist`: the preset configs without a container (`lineChartConfig`, `barChartConfig`, `pieChartConfig`), the series colors (`seriesColors`, kept equal to `$ct-series-colors` by a test) and the SVG label metric (`textAscent`). Third-party renderers get the same, and there is no extra package to version. A private shared package was considered and dropped, because its code would be copied into every package's build.
- **Package docs live on chartist.dev** under `/packages/<name>/` (decided 2026-10-15): an overview, the package's guides and one API page generated from its types, with a "Packages" item in the header. Their sources stay with the site, in `apps/docs/src/content/packages/<slug>/`, and `apps/docs/src/data/packages.ts` registers each package. Docs inside each package's folder were considered and left for later: guides import site components, and the site's checks assume its folders.
- **Packages use only `chartist`'s published entry points** and are tested from their build: unit tests, a test of their README's examples, and a smoke test that packs and installs them.
- **Packages are the author's own, free or paid** (decided 2026-10-18). Every `@chartist-js` package is made by Chartist's author; third-party work is a community plugin and is listed on `/plugins/`. Some packages are free, others commercial: a yearly license that includes support. The next one is a paid financial charts package. The site's package registry says which (`license`: `open-source` with the license name, or `premium` with its terms and where to get a license), and a premium package shows a license link instead of an install command. The site labels free packages "Open source" and doesn't mention paid packages until the first one is listed; then it presents them as premium packages (decided 2026-10-19), so the open source packages lead and the site doesn't read as a sales page. How paid packages are hosted, published and installed (a private repository, a private registry or license keys, checkout, and whether they join the lockstep release) is open and is decided before the first one; until then, the `@chartist-js` scope rule above (public, from this repository) covers the free packages.
- **The packages are shown on the landing page and in a showcase** (decided 2026-10-18): a news list below the hero announces new packages and releases (the three newest), a landing section draws one chart as SVG and as text art, and `/packages/` has a card per package with a preview the package renders at build time. A registry entry and a preview are all a new package needs to appear on both pages.

## Security

Decided 2026-10-16 (#1516).

- **Charts work under a strict Content Security Policy:** `style-src 'self'` without `'unsafe-inline'`, no `'unsafe-eval'`, and Trusted Types. Styles are set through the CSSOM (`element.style.cssText`), which a policy allows, and the markup keeps its `style` attributes, so 1.x output is unchanged. The library needs nothing beyond `'self'`; the terminal stylesheet needs `font-src data:` for its embedded font.
- **Chart data stays data in every output.** Text and attribute values are escaped, and `renderToString()` throws on an element or attribute name that isn't a valid XML name, as the DOM renderer does, rather than skipping it.
- **Plugins are the page's own code.** Chartist doesn't filter what they set (event handler attributes, `javascript:` URLs), and the 1.x `Svg#foreignObject()` keeps taking a string as HTML. The Security and CSP guide says so.
- **Rendering without `innerHTML`:** `chart()` and the DOM renderer build elements, and the terminal has `format: 'element'` (`renderToElement()`) for pages that forbid HTML strings. The string outputs stay for servers and Node.js.
- **Later, if asked for:** a named Trusted Types policy, so the string outputs can return `TrustedHTML`.

## Road to 2.0 final

Decided 2026-10-16. The functional API's names and surface are final as they are. What remains is which open issues land before 2.0: after 2.0 final, only additive changes go into 2.x minors, and anything that changes existing defaults, output or a documented promise waits for 3.0.

- **rc.3:**
  - #215 `labelTransform`, the new name of `labelInterpolationFnc`;
  - #1463 label and grid defaults that follow a dark `color-scheme`;
  - #262 an offset for `bar()`, for grouped stacks;
  - #1209 a trend line layer;
  - #1487 label alignment per axis on the presets;
  - #546 line breaks in pie labels, on by default.
  - #1516 security and CSP: charts under a strict policy and Trusted Types, and string output that data can't break.

  It ships soon after, so target lines, bands and layer refinement reach npm.

- **Live updates, without an rc.4** (decided 2026-10-17): #3 and #961 went in together, because patching changes when `render` and `mount` run and what a plugin has to undo; designing the cleanup hook before the renderer would have meant changing the plugin contract twice. They ship in 2.0.0 directly, not in a release candidate of their own: the RCs have stalled, waiting for feedback would take long, and feedback on live updates can be met without breaking anything.
- **2.0 final:** the core is final: the functional API, the pipeline, the scene, the renderer contract and the plugin lifecycle lose their `@experimental` tags, and so does `@chartist-js/terminal`. `chartist/live` stays experimental, and `container()` too, because it rests on a draft standard; both can become stable in a 2.x minor, since nothing rules out stabilizing an API in a minor. The experimental names are recorded in `packages/chartist/test/api/exports/experimental.json` and checked against the declarations, like the deprecated ones.
- **The `v2` label** marks what's planned for 2.x, 2.1 and later minors included, not only what fits before 2.0.0.
- **2.1 and later (additive):**
  - #64 log axis, #116 time axis (in `@chartist-js/essentials`);
  - #940 series class names without letters, once its API is designed;
  - opt-in options for behavior that would break as a default: #921 closing grid line, #304 axes sized to their labels, #1271 dropping overlapping labels;
  - the other open feature requests.
- **One exception to additive minors** (decided 2026-10-18): 2.1 moves `renderToString()` from `chartist` to the new `chartist/server`, without a deprecated re-export. 2.0.0 was a day old, the fix is one import path, and every full browser build (`index.min.js`, UMD, CDN links) gets about 1.1 kB smaller for good; a re-export would have kept those bytes until 3.0. It ships as a manual `2.1.0` release, with the move in the changelog's breaking section. Additive minors stay the rule.
- **Bars stay lines** (#522): the presets keep the 1.x `<line>` markup, and so does `bar()`. Bars with a fill and a stroke are a plugin's job, not a later core change.

## Live updates

Decided 2026-10-16 and 2026-10-17 (#3, #961).

- **Opt-in, in its own entry point.** Patching and update animations would add about 3.5 to 4 kB gzipped to every chart (`chart()` +75%), and most charts render once. So they live in `chartist/live`, built like `chartist/compat`; the core grew about 0.6 kB. Measured: `liveDomRenderer()` adds 1.35 kB to a chart, `smilAnimations()` about 4 kB more.
- **A renderer, not a plugin.** Plugins can't make a renderer patch, reach the previous output or change the `render` and `mount` payloads, so a plugin would have needed a private hook. Charts opt in with `renderer: liveDomRenderer()`, on `chart()` and on the presets, which take a `renderer` for it.
- **State lives with the chart; renderers are stateless.** From the second render on, a renderer gets the previous render (its own previous output, the previous scene, the cause, both renders' labels and a keyframes lookup) and returns `patched` and its `changes`. One renderer can serve many charts, and a canvas renderer could patch through the same contract. Without `patched`, `render` and `mount` describe a replacement.
- **The pipeline computes everything on every run.** One changed value moves most nodes anyway (scales, step axes, stacks, pie totals), so stages don't compute deltas. Identity is the live renderer's business: values by `key` (`index`, `label` or a function), ticks by value, groups by layer and class. The scene's keys didn't change.
- **Updates animate with SMIL.** CSS can't move `<line>` attributes, and Safari doesn't transition `d`. Animations are additive offsets over the final attribute values, so an interrupted animation continues without a jump and the DOM always holds the new state. Easings SMIL can express are `keySplines`; the others, including overshooting ones, are sampled into frames. Timing is CSS: `--ct-update-duration` and `--ct-update-easing`, 300 ms `ease-out` when unset, `0s` turns it off; reduced motion always wins.
- **Keyframes come from plugins, then the layer.** SMIL only morphs paths with the same commands, so lines, areas and bands need keyframes when keys or counts change, and pie slices whenever their angles change. The built-in ones ship in `smilAnimations()`, not in the layers.
- **Shared code goes through core exports** (`renderElement()`, `applyAttribute()`, `sampleEasing()`, `keySplinesOf()`), as for the maintained packages: a module shared at build time would be bundled into both `index.min.js` and `live.min.js`.
- **1.x code always gets a new SVG.** The 1.x classes and charts with compat or converted 1.x plugins never get the previous render, even with `liveDomRenderer()`, because 1.x `draw` listeners expect new elements.
- **Firefox runs no SMIL inside a `foreignObject`,** so HTML labels move without an animation there; animations that didn't start are removed.

## Hydration

Decided 2026-10-18.

- **Server markup is taken over, not drawn again.** `renderForHydration()` (from `chartist/server`) renders markup that `chart()` and the presets take over in the browser: the elements stay, so CSS animations that started with the page continue, a lazily loaded Chartist leaves no blank frame, and LCP stays at first paint. A proof of concept in Next.js, Nuxt, Angular and SvelteKit showed it needs no framework-specific code in Chartist.
- **Two server outputs.** `toScene()` + `renderToString()` stay the self-contained SVG image, with inline styles, for files, PDFs and email. Hydration markup has no `style` attributes: what SVG can express becomes presentation attributes, the stylesheet sizes label spans, and the rest is applied at the takeover. So it passes `style-src 'self'`, and the page needs Chartist's stylesheet.
- **Adoption is a renderer capability, in `chartist/live`.** `Renderer.adopt(container, replay)` finds the marked svg and reads its marker; the core only replays the server's scene (the config without responsive overrides, the recorded size and label mode, the text estimate) and runs `render` and `mount` with the cause `hydrate`. The DOM renderer doesn't adopt, since it replaces its svg on every render. Keeping the marker lookup out of the core kept `lineChart` at +0.295 kB gzipped; with it in the core, it was +0.58 kB.
- **The correction is a `resize`.** After the `hydrate` mount, the chart lays out at the container's real size through the normal path; when the live renderer patched nothing, the chart emits nothing, so at the server's size there's one mount. That relayout isn't animated.
- **Strict structure, repaired values.** A different structure warns and draws a new svg; different values are set and counted in `hydration.repaired`, which is 0 for the same data and options.
- **A warning when other code replaced the svg,** checked at the start of each render: every framework's raw-HTML feature writes server markup again in some situation, which silently broke live updates.
- **Recipes, not wrapper packages.** The "Charts in frameworks" guide gives the rule (render the markup once, create the chart after hydration, update through the handle, destroy on unmount) and recipes for React, Vue, Angular and Svelte. A web component, the standing plan for framework support, would build on the same contract.
- **Community wrappers are listed, not maintained** (2026-10-19). The README, the package README, the frameworks guide and the landing page list the community's framework wrappers from `apps/docs/src/data/ecosystem.ts`, each with the Chartist version it's built for. A wrapper is listed with at least about 20 GitHub stars or 500 npm downloads a month, and only while its repository isn't archived: readers shouldn't land on a dead end. Forks, republished copies of the library and apps that only use Chartist aren't wrappers.
- **The server can't know the reader's width,** so the docs explain choosing one size (the most common container width) and what client hints or a cookie leave. The landing page's hero chart is rendered at build time at the board's desktop size, as the site's own test of the feature.

## Server rendering

Decided 2026-10-18.

- **Its own entry point, `chartist/server`,** for what turns charts into markup: `renderToString()`, `renderForHydration()`, `computeStyles()` and `applyStyles()`, experimental from 2.1 on. Built like `chartist/live`, it imports the core instead of bundling it. Server code never needed the serializer in every browser bundle.
- **`toScene()` stays in the core,** and `chartist/server` re-exports it. It runs on the pipeline's internals, which the core doesn't export, so moving it would have meant a second pipeline in `chartist/server` or exported internals, for 0.16 kB. It's browser code too: `diffScenes()`, the terminal package, `domRenderer().render(scene)`.
- **Styles for SVG on its own are written as attributes.** Rasterizers and PDF tools ignore custom properties and `light-dark()`, which Chartist's stylesheet colors series with, and a series' color depends on the group a line is in. So styles are computed per element and written as presentation attributes, not copied into a `<style>` element.
- **A small CSS engine, and a seam for a full one.** `computeStyles()` reads what chart styles use (classes, descendant and child selectors, `:root`, the cascade, custom properties, `light-dark()`, `prefers-color-scheme`) and reports what it leaves out through `onSkip`. A complete CSS engine needs a browser, so `applyStyles()` takes the computed styles of any engine; the guide shows one that uses headless Chromium. The limits are documented instead of growing the engine.

## Releases

- **Versions:** release candidates were `2.0.0-rc.N` (with the dot, so `rc.10` sorts after `rc.9`) under the npm `next` dist-tag. `2.0.0` is published under `latest` from a manual run with that version (decided 2026-10-17); afterwards `RELEASE_PREID` is unset, so versions follow the conventional commits. A later prerelease sets it again and goes under `next`.
- **Small minors** (decided 2026-10-19): after 2.1, each minor ships a few fixes and features rather than waiting for a large set, so they reach users sooner and each release stays easy to review. The plan is kept on GitHub as one milestone per version (`2.2.0`, `2.3.0`, …); the triage labels keep saying where a change belongs and how big it is, with `essentials` and `tooltips` added for the two packages.
- **Tooling:** `nx release` with conventional commits: the version, the workspace `CHANGELOG.md` (continuing the 1.x one), `v{version}` tags as in 1.x, the GitHub release and the npm publish.
- **Lockstep:** `chartist` and the `@chartist-js` packages are one fixed release group (decided 2026-10-15): one version for all, one tag, one changelog section and one GitHub release, published by the same workflow. Independent versions were considered; lockstep keeps one version to explain and one release to approve. A new package needs a trusted publisher on npmjs.com (repository `chartist-js/chartist`, workflow `release.yml`, environment `release`) before its first release; `@chartist-js/terminal` has had one since `2.0.0-rc.2`.
- **Changelog:** it covers the released packages only. A renderer on top of Nx's default (`tools/changelog-renderer.cjs`) leaves out commits scoped `docs`, `playground`, `examples` and `openspec`, which ship with the site, and the authors section is off. `docs`, `test`, `build`, `chore`, `refactor`, `style` and `ci` commits neither bump the version nor appear. Commit subjects may start with a name (`LineChart wraps …`), so commitlint doesn't check their case.
- **Version choice:** in order, the manual run's version, the next prerelease of the repository variable `RELEASE_PREID` (`rc` during RCs) when the current version is one, or the conventional commits. An automatic run on a final version while `RELEASE_PREID` is set stops instead of publishing `x.y.z-rc.0`. The logic is a tested script, `.github/scripts/release.mjs`.
- **Approval:** the release workflow runs after green CI on `main` and waits for the author's approval in the `release` environment. A manual run can set the version, do a dry run, or re-publish a tagged version.
- **npm:** trusted publishing via OIDC, so there is no stored token and provenance is attached. Prereleases are published under `next`, final versions under `latest`. A local `nx release` is only ever a dry run: the configuration pushes.
- **Pushing to protected `main`:** `main` keeps its protection (reviewed pull requests, no force pushes). The release pushes its commit and tag as a GitHub App ("Chartist Release") on the protection's bypass list, with its key stored as `release` environment secrets, because `GITHUB_TOKEN` can't bypass the protection and deploy keys aren't bypass actors.
- **Install instructions:** while the version is a prerelease, the site turns `npm install chartist` into `chartist@next` (and `@chartist-js/terminal` into `@chartist-js/terminal@next`) and pins CDN URLs to the exact version (ranges like `chartist@2` skip prereleases). The page sources keep the 2.0.0 wording.
- **Docs deployment:** `docs.yml` deploys chartist.dev from `main` while the repository variable `DOCS_DEPLOY` is `true`, and waits until the built version is on npm, since the release commit is pushed just before the publish.

The workflows and settings are specified in the `release-process` and `continuous-integration` specs.

## Docs hosting

- **chartist.dev** serves the v2 site, from `2.0.0-rc.1` on, deployed to GitHub Pages from `main`.
- **`/v1/`** holds the 1.x docs as the static output of their last Docusaurus build; no Docusaurus stack is kept. Old 1.x URLs that v2 doesn't have redirect there.
- **`/v0/`** holds the 0.x docs, copied from the last build on the `gh-pages` branch of `gionkunz/chartist-js` without the affiliate block, the analytics and the version pop-up, and with self-hosted fonts, so they make no requests to other hosts. The version switcher and the footer link both archives.
- **The old 0.x site** (https://gionkunz.github.io/chartist-js/) redirects to chartist.dev with a page per old page: canonical link, script and instant meta refresh, since GitHub Pages can't send HTTP redirects. A page without a `#hash` goes to its v2 counterpart, an anchor v2 covers to that page, any other anchor to the same place under `/v0/`. `docs:v0-redirects` checks the targets against the build and writes the pages; a renamed v2 page or heading means running it again and pushing the result to that `gh-pages` branch.
- **Diagrams are Mermaid,** written as `.mmd` files next to the docs, imported with `?raw` and shown with a `Diagram` component (decided 2026-10-18). They're rendered to SVG during the docs build, in Playwright's Chromium, since Mermaid measures text with a browser's layout engine and Node has none; a cache keeps rebuilds fast, and the docs workflow installs Chromium before it builds. Mermaid's own styles are removed: the site's tokens style the diagrams, so one inline SVG follows light and dark mode. Pages load no Mermaid script. `with { type: 'text' }` replaces `?raw` once Vite supports it.
- **Visitor counting:** GoatCounter (`chartist.goatcounter.com`), cookieless, so no consent banner. It loads only on chartist.dev, so dev, tests, previews and forks never request it, and it's the one exception to "no third-party requests" (fonts and assets are self-hosted). The `/v1/` archive isn't counted.

## Test strategy

- **The library is tested rigorously; the docs site gets happy paths** (decided 2026-10-16). Chartist's tests guard what users rely on: unit and public API tests, the 1.x parity tests and the API tests against 1.5.0, pixel comparisons with 1.5.0, the bundle size budgets and the package smoke tests. The docs e2e tests check that each page loads without errors or third-party requests, that every live example runs, and the site's interactive features and published URLs. They don't pin copy, ordering or per-page details.
- **One page per template** is enough where pages share a template: the accessibility scan opens one page per template (plus pages with components of their own) on every push, and every page only before a release. Checks of static output (share tags, the sitemap) read the built HTML instead of opening a browser per page.
- **CI checks each thing once:** the Node matrix covers the packages; the docs site is built and tested in its own workflow.

## Visual regression

- **Reference platform:** Linux x64 with the Chromium of the pinned Playwright version: GitHub's Ubuntu runners or the author's WSL2 host. Committed baselines (`packages/visual/__screenshots__`) are recorded only there.
- **The dev container's fonts render differently,** so it never records committed baselines. It uses `visual:test:visual:local`, against a local baseline made from 1.5.0 by `visual:test:visual:local-baseline`. Examples without 1.x code get their local baseline from the current build, so for those, check the committed images instead.
- Considered for later: running the visual tests in the official Playwright Docker image, so every machine matches the reference platform.

## Standards to monitor

Check these before each release and update the docs and the polyfill advice when they move.

- **`Element.matchContainer()`** ([csswg-drafts#6205](https://github.com/w3c/csswg-drafts/issues/6205)), the `@container` counterpart of `matchMedia()`, used by container conditions in responsive options. Until browsers ship it, users load the [`match-container`](https://github.com/teetotum/match-container) polyfill, and container conditions are documented as experimental and polyfill-only; every container example shows the polyfill import and the `container-type` CSS. Chartist depends only on `matchContainer(query).matches` and an optional `change` event. Watch for the final name and semantics, a `change` event or observer, and browser releases.
