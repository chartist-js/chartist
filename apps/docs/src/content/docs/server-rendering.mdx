A Chartist chart doesn't need a browser until the very end. The pipeline builds a scene, a plain tree of SVG elements, and only the last step writes it into the page. Stop before that step, and you can render the scene to a string anywhere JavaScript runs: in Node.js, in a server bundle, in a worker.

## Two outputs

What you render depends on where the markup goes:

- **A self-contained SVG image**, from `toScene()` and `renderToString()`. It's a picture of the chart for files, PDFs, email, social images or a static chart in a page. It carries its inline styles, since there's often no stylesheet where it ends up.
- **Hydration markup**, from `renderForHydration()`. It's a page fragment that the browser [takes over](#taking-charts-over-in-the-browser): the chart is in the server's HTML, and once the page's script runs, it keeps its elements and gets updates, plugins and animations. It has no inline styles, so it needs Chartist's stylesheet in the page, and it passes a strict `style-src` policy.

The rest of this page starts with the image, then takes a chart over.

## Two functions

`toScene(config, size)` runs the pipeline from `resolve` to `scene` and returns the scene. It takes the same config as `chart()`, with your plugins and listeners, plus the size to lay out at. It touches no DOM, timers or globals.

`renderToString(scene)` turns a scene into standalone SVG markup, namespaces included.

```ts
import { lineChartConfig, renderToString, toScene } from 'chartist';

export function weekChart(values: number[]): string {
  const scene = toScene(
    lineChartConfig({
      labels: ['Mon', 'Tue', 'Wed', 'Thu', 'Fri'],
      series: [values]
    }),
    { width: 600, height: 300 }
  );
  return renderToString(scene);
}
```

The presets (`lineChart()` and friends) draw into an element. For their charts as a string, `lineChartConfig()`, `barChartConfig()` and `pieChartConfig()` build the config a preset draws, from the same data and options: `toScene(lineChartConfig(data, options), size)`. `toScene()` takes any config of `chart()`, so [composed charts](../composed-charts/) with their own axes and layers render the same way.

The browser can run the same code. This example builds the scene with `toScene()` and shows its markup from `renderToString()` below the chart. The chart itself comes from the same scene through `domRenderer()`: in a page, the DOM renderer creates the elements, so nothing goes through `innerHTML`, which [a strict Content Security Policy](../security-and-csp/) can block.

## Size

A server has no container to measure, so you pass the size: the scene is laid out at `width` × `height`, and the root `svg` gets those as its `width` and `height`. To let the markup scale with its container, add a `viewBox` of the same size to the config, as the example does, and size the SVG with CSS:

```css
.chart svg {
  width: 100%;
  height: auto;
}
```

## Measuring text

SVG labels (see [below](#svg-or-html-labels)) are wrapped into lines and aligned by Chartist, so it needs to know how wide text is. In the browser, it measures the text with the page's fonts. On a server, `toScene()` estimates it: each character is 0.6 em wide and a line 1.2 em high, at 12px unless told otherwise. That's close enough for numbers and short labels.

When you know your fonts, pass a `measureText` function in the size, next to `width` and `height`. It gets the text and options with the `fontSize` (and the label's `classes`), and returns a `width` and `height` in px:

```ts
import type { MeasureText } from 'chartist';

// Wider glyphs than the estimate, for a wide font.
export const measureText: MeasureText = (text, options = {}) => {
  const fontSize = options.fontSize ?? 12;
  return { width: text.length * fontSize * 0.7, height: fontSize * 1.25 };
};
```

Then call `toScene(config, { width: 600, height: 300, measureText })`.

## SVG or HTML labels

Chartist draws axis labels in one of two ways, set with the `labels` option:

- `html`: a `<span>` inside a `<foreignObject>`, as 1.x did. CSS lays them out, wraps long text and aligns it with flexbox. Only browsers draw them.
- `svg`: an SVG `<text>`, wrapped and aligned by Chartist. Every SVG viewer draws these.

The renderer picks the default: `chart()` and the presets draw HTML labels in the page, and `toScene()` draws SVG labels, because string output often ends up in tools without HTML support. Set `labels` to choose for yourself, in the config (`labels: 'html'`) or in the size of `toScene()`. The config wins.

`axisLabels()` takes `labels` too, for one layer, and so do `lineChart()` and `barChart()` as an option. The 1.x classes always draw HTML labels, and pie and donut labels are always SVG text.

## Where the markup goes

The markup has the same classes as a chart in the page, but no styles. Where it ends up decides how it gets them.

**Server-rendered pages.** Put the string into your HTML and load `chartist/styles.css` (or your own chart styles) on the page, like for any chart. Since the page is HTML, HTML labels work, if you want them. If the chart should run in the page once its script loads, render [hydration markup](#taking-charts-over-in-the-browser) instead.

**PDFs.** If you print HTML to PDF with a headless browser, it's the same as a web page. Other PDF tools read the SVG on its own: there, use SVG labels and put the styles into the SVG.

**Email and images.** Many email clients don't show SVG at all, so send a PNG. Convert the markup with an SVG rasterizer, for example in a Node.js service, and use SVG labels with the styles inside the SVG. Rasterizers support less CSS than browsers: keep those styles to plain selectors and values.

To put styles into the SVG, add a `<style>` element to the scene with a `scene` listener:

```ts
import { lineChartConfig, node, renderToString, toScene } from 'chartist';

const css = `
  .ct-grid { stroke: #ccc; stroke-dasharray: 2px; }
  .ct-label { fill: #666; font: 12px sans-serif; }
  .ct-line { fill: none; stroke: #d70206; stroke-width: 4px; }
  .ct-point { stroke: #d70206; stroke-width: 10px; stroke-linecap: round; }
`;

const scene = toScene(
  lineChartConfig(
    { labels: ['Mon', 'Tue', 'Wed', 'Thu', 'Fri'], series: [[12, 9, 7, 8, 5]] },
    {
      on: {
        scene: ({ scene }) => ({
          scene: scene.append(node('style').text(css), true)
        })
      }
    }
  ),
  { width: 600, height: 300 }
);

export const markup = renderToString(scene);
```

<Callout>
  **Plugins run on the server too.** `toScene()` installs the config's plugins
  and calls their listeners, up to the `scene` phase. Plugins that change the
  scene work there unchanged; listeners of `render` and `mount` never run, and
  calling `update()`, `detach()` or `destroy()` throws. 1.x plugins converted
  with `fromLegacyPlugin` don't run there: their `draw` and `created` events
  come from the `mount` phase. See [Events and plugins](../events-and-plugins/).
</Callout>

## Taking charts over in the browser

A chart in the server's HTML shows up with the page's first paint. To make it a live chart afterwards, without drawing it again, render it on the server with `renderForHydration()` and create the chart in the same container in the browser, with the same data and options:

```ts
import { lineChartConfig, renderForHydration } from 'chartist';

const data = {
  labels: ['Mon', 'Tue', 'Wed', 'Thu', 'Fri'],
  series: [[12, 9, 7, 8, 5]]
};

// On the server, inside the chart's container: <div id="chart">…</div>
export const markup = renderForHydration(lineChartConfig(data), {
  width: 600,
  height: 300
});
```

```ts
import { lineChart } from 'chartist';
import { liveDomRenderer } from 'chartist/live';

const data = {
  labels: ['Mon', 'Tue', 'Wed', 'Thu', 'Fri'],
  series: [[12, 9, 7, 8, 5]]
};

// In the browser: the chart keeps the server's svg and its elements.
const chart = lineChart('#chart', data, { renderer: liveDomRenderer() });
chart.update({ data: { ...data, series: [[3, 9, 7, 8, 11]] } });
```

The browser doesn't read the data from the markup: it builds the same scene again from its own config, at the size the server recorded, and binds it to the server's elements. From there on, it's a chart like any other. The example's page holds the server markup in its `index.html`, and **New values** updates the chart it became:

### Keep it with the live renderer

`liveDomRenderer()` from `chartist/live` takes the markup over: the elements stay, and so does what the page did with them. A CSS animation that started with the page continues, and a lazily loaded Chartist leaves no blank frame. With the default renderer, which draws a new svg on every render, the chart draws a new svg over the server's. That works too, but the animation starts again. `liveDomRenderer({ adopt: false })` does the same, for a chart that wants live updates but not the server's elements.

### The hydrate render

The takeover is the chart's first render: `render` and `mount` run with the cause `hydrate`, and `mount` gets the server's elements, so plugins work on them as on a first render. The events also carry `hydration.repaired`: how many attributes, classes and texts of the markup differed from what the browser built. It's 0 when the server and the browser drew the same data and options. Log it in development to catch the two drifting apart:

```ts
import { lineChart } from 'chartist';
import { liveDomRenderer } from 'chartist/live';

lineChart(
  '#chart',
  { labels: ['Mon', 'Tue', 'Wed'], series: [[12, 9, 7]] },
  {
    renderer: liveDomRenderer(),
    on: {
      mount: ({ cause, hydration }) => {
        if (cause === 'hydrate' && hydration?.repaired) {
          console.warn(`The server drew ${hydration.repaired} differences`);
        }
      }
    }
  }
);
```

Values that differ are set, and the chart shows the browser's. A different structure, such as a point more, can't be kept: the chart warns, names the first difference and draws a new svg.

### Size in the browser

A server has no container to measure, so it lays the chart out at the size you give it and records that size. The markup's svg is `100%` wide and high (unless the config sets a size), with a `viewBox` of the server's size, so the drawing scales into its container until the chart runs. Then the chart lays itself out at the container's real size.

How close the two sizes are decides what readers see at the takeover:

- **The same size:** nothing is drawn again. The chart keeps the server's layout, and the takeover is invisible.
- **A narrower container:** before the chart runs, the whole drawing is scaled down, text and lines included: a 600 px wide layout in a 343 px phone column shows 12 px labels at about 7 px. At the takeover, the chart lays out again at 343 px, so the labels get their real size and the points, grid lines and labels move. An auto-scaled axis can also get fewer ticks, since it keeps them at least `scaleMinSpace` px apart.
- **A wider container:** the same, scaled up before the takeover.

The elements stay either way: the chart changes them instead of drawing new ones. Responsive options apply only from the takeover on too, since the server draws without them.

So pick the server's size for the readers you have: the width your layout gives the chart most often, for example its column on a desktop, or a phone's width if most of your readers come on phones. The server can't know a reader's width; sending a size per device (from client hints or a cookie) is up to your app. HTML labels that move at the takeover count as a small layout shift (CLS), around 0.002 to 0.03 in our tests; SVG labels don't.

Give the container a height or an `aspect-ratio` that matches the server's size, and make the svg a block, as for every chart that fills its container:

```css
#chart {
  aspect-ratio: 2 / 1;
}

#chart svg {
  display: block;
}
```

With a matching `aspect-ratio`, the server's drawing fills the container exactly; with another one, it sits letterboxed inside it until the takeover. Without a height, the server markup looks right, but the chart collapses to 150 px once it runs, as it would without server rendering. See [Sizing charts](../sizing-charts/).

### Styles and text

Hydration markup has no `style` attributes. Chartist's stylesheet sizes the label boxes and the root's attributes size the svg; a donut's `donutWidth` becomes a `stroke-width` attribute. So the markup looks the same before and after the takeover, and it passes a policy of `style-src 'self'` (see [Security and CSP](../security-and-csp/)). Styles that your `scene` listeners add appear only once the chart runs: for what should show before, use classes and CSS.

Use the built-in text estimate on the server, without a `measureText`: the browser replays the server's layout with it.

### Render the markup once

The chart owns its svg after the takeover. Code that writes the server markup into the container again, as some frameworks' raw-HTML features do when a page updates, leaves the chart drawing into an svg that's no longer on the page. Chartist warns on its next render and draws a new svg, but the fix is to render the markup into the container only once. [Charts in frameworks](../frameworks/) shows how, in React, Vue, Angular and Svelte.
